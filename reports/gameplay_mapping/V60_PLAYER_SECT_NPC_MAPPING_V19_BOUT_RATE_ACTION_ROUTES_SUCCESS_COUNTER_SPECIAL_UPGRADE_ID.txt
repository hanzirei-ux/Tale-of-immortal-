1. V19 EXECUTIVE RESULT
====================================================================================================

V19 closes four important questions and corrects one important V18 interpretation.

A) V60 contains exactly four BoutExhausted payload literals in its metadata literal pool:
     boutExhausted_5000_exhaustedLog90010022
     boutExhausted_5000_exhaustedLog90020011
     boutExhausted_5000_exhaustedLog90020021
     boutExhausted_5000_exhaustedLog90020031

   WorldUnitEffectSpecialBoutExhausted.Create already proved the parser semantics:
     values[0] -> rate
     values[1] -> key

   Therefore every one of these four payload variants encodes:
     rate = 5000
   and RunUnit interprets that as:
     Random(0,10000) < 5000
     => 50% trigger chance PER ACTIVE BoutExhausted effect, per checked goal attempt.

B) Action1052/1053/1054/1055 are NOT hidden alternate branches of Goal141.

   Metadata + method-RVA mapping gives:
     Goal141 -> Action1051 -> UnitActionRoleSeekUpGrade
     Goal142 -> Action1052 -> UnitActionRoleHelpSeekProp
     Action1053 -> UnitActionRoleJealous
     Action1054 -> UnitActionRoleTeachSkill
     Action1055 -> Goal145-style reward/item logic

   Thus the major-breakthrough material path mapped through Action1051 is the correct direct family.

C) MAJOR V18 CORRECTION:
   seekGradeNeedNum is NOT a "failed seek count" threshold.

   UnitActionRoleSeekUpGrade.OnEnd only constructs/invokes its progression callback after:
     isTargetComplete == true
     AND
     isDungeonComplete == true.

   The callback then increments WorldUnitAIDataBase +0x158 for ordinary NPC->NPC isUpGrade seeks.

   So +0x158 is best described as a SUCCESSFUL-SEEK progression count for this mapped path.
   First-gate failures do NOT increment it.

   Current exact Player-Sect seekGradeNeedNum=1 therefore means:
     after the FIRST qualifying successful seek, native AddUpGradeProps is already eligible.

D) This moves the strongest remaining delay one step earlier:
   UnitActionRoleSeekUpGrade.NPCToNPCAction FIRST target/cooperation gate.

   If that first gate fails:
     - isTargetComplete=false;
     - dungeon-success=100 is never reached;
     - +0x158 does not advance;
     - seekGradeNeedNum=1 cannot help on that attempt.

   Once the first gate succeeds:
     - Player-Sect dungeon threshold is forced to 100;
     - the success callback can increment +0x158 to 1;
     - native AddUpGradeProps can become eligible immediately.

E) UnitActionRoleUpGradeRule and UnitActionRoleUpGradeElder use separate special-upgrade logic.
   Neither audited class routes through ordinary UnitActionRoleUpGrade.GetCompleteRate.
   Therefore the current Player-Sect ordinary 100% completion helper must NOT be claimed to cover
   Rule/Elder special breakthrough classes.

2. BOUTEXHAUSTED — EXACT V60 PAYLOAD SET AND RATE
====================================================================================================

V18 mapped:
  WorldFactory.CreateEffectSpecialBase      @ 0x0565E9D4
  literal branch "boutExhausted"            ~ 0x05660D98
  WorldUnitEffectSpecialBoutExhausted.Create @ 0x05553958

Runtime fields:
  BoutExhausted.rate +0x80
  BoutExhausted.key  +0x88

Create semantics:
  configured special values[0] -> integer rate
  configured special values[1] -> log key

V19 directly parsed the V60 metadata string-literal table and found exactly four literals beginning
with "boutExhausted_":

  #155215  boutExhausted_5000_exhaustedLog90010022
  #155216  boutExhausted_5000_exhaustedLog90020011
  #155217  boutExhausted_5000_exhaustedLog90020021
  #155218  boutExhausted_5000_exhaustedLog90020031

The matching standalone log-key literals also exist:
  exhaustedLog90010022
  exhaustedLog90020011
  exhaustedLog90020021
  exhaustedLog90020031

Since RunUnit uses:
  Random(0,10000)
and integer max is exclusive:
  random = 0..9999

For one active one of these effects:
  P(BoutExhausted intercept) = 5000 / 10000 = 0.5 = 50%.

For N simultaneously active matching effects:
  P(any intercept) = 1 - product_i(1 - rate_i/10000)

If all N use the observed 5000 rate:
  N=1 -> 50%
  N=2 -> 75%
  N=3 -> 87.5%
  N=4 -> 93.75%

IMPORTANT:
This does NOT mean every NPC has a permanent 50% skip chance.
The effect must first be attached/active on that WorldUnit.
V19 proves the configured payload values, not the runtime prevalence of the effect.

5. seekGradeNeedNum — V18 FAILURE-COUNTER INTERPRETATION IS WRONG
====================================================================================================

Action:
  UnitActionRoleSeekUpGrade

Important fields:
  target WorldUnit          inherited +0x38
  isTargetComplete          +0x9A
  isDungeonComplete         +0x9B
  isRob                     +0x9C
  isRobIdea                 +0x9D
  isRobComplete             +0x9E
  itemGrade                 +0xA0
  targetGradeId             +0xA4
  targetPropId              +0xA8
  isUpGrade                 +0xAC

OnEnd:
  UnitActionRoleSeekUpGrade.OnEnd @ 0x0550C334

Critical checks:
  0x0550C3BC  reads isTargetComplete
  0x0550C3D0  reads isDungeonComplete

Only when both are true does this path build the progression callback that reaches:
  UnitActionRoleSeekUpGrade.<OnEnd>b__17_0 @ 0x055105C0

Thus:
  first target gate fail  -> no progression callback
  dungeon gate fail       -> no normal successful-seek callback
  both complete           -> callback becomes reachable

Inside b__17_0, the ordinary pure-NPC path excludes player-involved cases and then obtains:
  WorldUnitAIDataBase

Counter operations:
  0x05510824  LDRB W8,[AIData,#0x158]
  0x0551082C  ADD  W22,W8,#1
  0x05510830  STRB W22,[AIData,#0x158]

Then:
  ConfNpcGoal141Base.seekGradeNeedNum is read
  current patch site 0x05510854 -> custom helper 0x08C7879C
  exact current Player-Sect threshold = 1

When the incremented counter reaches the threshold, native:
  UnitActionRoleSeekUpGrade.<OnEnd>g__AddUpGradeProps|17_1 @ 0x055109C4
can be called.

A later branch can reset the same counter:
  0x055109A8  STRB WZR,[AIData,#0x158]

CORRECT SEMANTIC DESCRIPTION:
  +0x158 is a successful qualifying seek count for this mapped NPC->NPC upgrade route.

It is NOT supported to call it:
  "number of failed seeks."

This corrects V18 sections that described:
  failed seek -> counter++ -> fallback.

The corrected model is:
  successful target cooperation
      -> successful dungeon
      -> successful-seek callback
      -> counter++
      -> if counter >= seekGradeNeedNum
           native AddUpGradeProps can supply required configured material.

With current Player-Sect threshold=1:
  ONE qualifying successful seek is sufficient.

6. WHY THE FIRST TARGET/COOPERATION GATE IS NOW THE MAIN MAPPED DELAY
====================================================================================================

UnitActionRoleSeekUpGrade.NPCToNPCAction @ 0x0550D7D4

FIRST gate:
  base:
    ConfNpcGoal141Base.okBaseRate

Native modifiers include:
  npcGradeRate1/2/3
  itemGradeRate1/2/3
  beautyRate1..7
  intimAddRate
  familyAddRate
  Action1051 trait/config context

First draw:
  Random(0,100) @ 0x0550E290

Result:
  isTargetComplete store @ 0x0550E29C

If random >= computed first threshold:
  the code leaves before the second/dungeon success path.

SECOND gate:
  Random(0,100) @ 0x0550E2C4

Current exact Player-Sect helper:
  hook site 0x0550E378 -> 0x08C78770
  selected dungeon threshold -> 100

Result:
  isDungeonComplete @ 0x0550E380

Therefore:

CASE A — first gate FAILS
  isTargetComplete = false
  -> dungeon 100% helper is irrelevant
  -> successful-seek callback not created/invoked
  -> +0x158 does not increment
  -> seekGradeNeedNum=1 does not activate AddUpGradeProps this attempt

CASE B — first gate PASSES
  -> second gate reached
  -> Player-Sect dungeon threshold = 100
  -> isDungeonComplete becomes true
  -> successful-seek callback can run
  -> +0x158 becomes 1
  -> threshold 1 allows AddUpGradeProps immediately

This makes the first target/cooperation RNG the strongest remaining RANDOM delay in the mapped
ordinary NPC->NPC Goal141 -> Action1051 material route.

This does NOT yet justify globally forcing it to 100, because its threshold intentionally contains
social/grade/beauty/relationship logic and the same action family may be used in contexts that
should remain native.

9. PATCH IMPLICATION AFTER V19
====================================================================================================

DO NOT PATCH YET:
  - do not increase quota above 19;
  - do not force BoutExhausted.rate globally;
  - do not delete role features 9001002 / 9002001/2/3 globally;
  - do not change seekGradeNeedNum lower than 1 (1 is already immediate after first qualifying seek);
  - do not patch passSufferingProb;
  - do not globally force first target/cooperation threshold to 100;
  - do not claim Rule/Elder are already guaranteed by ordinary GetCompleteRate=100.

Why:
  - V19 shows seekGradeNeedNum is already as aggressive as useful: threshold 1.
  - failure before that counter is the first target gate, not "too many failed seeks required."
  - a broad first-gate patch would erase relationship/grade/beauty mechanics for unrelated NPCs.
  - BoutExhausted 50% is meaningful when active, but runtime attachment prevalence/source rows are not
    yet completely mapped.

If a future patch is justified, the safest candidate architecture is likely:
  exact current Player-Sect
  AND Action1051 / UnitActionRoleSeekUpGrade
  AND isUpGrade=true
  AND pure NPC->NPC route
  -> selectively increase/min-floor only the FIRST target/cooperation threshold.

That is far narrower than changing CommonTool.Random, ConfNpcGoal141 globally, or all social actions.
