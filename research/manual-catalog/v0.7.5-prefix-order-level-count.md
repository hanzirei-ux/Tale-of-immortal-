# Tale of Immortal Android — v0.7.5 Prefix Ordering and Level Count

**2026-11-01 — Read-only research.** Mod Menu v0.3.6, DEX, APK, JNI, native libraries and saved game unchanged. Rarity excluded.

## New verified end-to-end prefix order

The earlier v0.7.4 name-selector report found that reversing the prefix order changes 174/183 candidate names. We have now traced the exact **forward order** from the original save to the code that computes the name.

- `MartialInfoData.GetPrefixs` at `0x45c1560` starts scanning `PropsData.values` at **index 6** (`0x45c1688`); each step advances the source index by 1 (`0x45c187c`), treats `-1` as a block separator (`0x45c16ac`), looks up configuration objects at `0x45c17e4`, and appends to its list (`0x45c1830`) in original order.
- `MartialInfoData.get_prefixs` at `0x45c1524` caches the newly built list at `+0x98` (`0x45c154c`).
- `ConfBattleSkillPrefixName.GetTotalValue` at `0x52c0f78` reads that cached list (`0x52c1040`), iterates forward starting from index **0** (`0x52c1078`), and advances by one (`0x52c12a8`). Its position-dependent contribution `number × (index+2)` therefore uses native list order, not reversed or sorted ID order.
- The **original archived `DataUnit.cache` was decoded again**, not just compared to a prior JSON file: all **183/183** derived records match v0.7.4 exactly for Martial Type, BaseID, Grade, **ordered prefix IDs**, and **ordered raw prefix values**. Zero differences.

This substantially resolves the previous order assumption. The English name candidate rendering still requires at least one live game UI comparison before treating any name as final.

## New Level finding

The third input to `ConfBattleSkillLevel.GetLevel` (`0x52bfee4`) is the **size of the same cached prefix list**:

- `SkillInfoData.GetLevel` (`0x584109c`) calls `get_prefixs` at `0x584113c`.
- It invokes a virtual Count getter on that list (`0x58411a4`) and passes its return value as `w3` (`0x58411ac`) to `ConfBattleSkillLevel.GetLevel` (`0x58411cc`).
- The static vtable token used to obtain the Count call is the same as in `GetTotalValue`, which compares list Count to its loop index.
- **Input 1** still comes from an unresolved `SkillInfoData` virtual method (vtable slot `+0x1e8`); **input 2** comes from the skill configuration field `+0x34`. Their difference determines which threshold table is selected. We do not know their values for each saved instance.
