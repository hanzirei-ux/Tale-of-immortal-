## Verified extraction

The gzip-compressed `DataUnit.cache` from the previously supplied `file 3.zip` was read without editing the save. The parser recognizes typed `PropsData.values` arrays containing Martial Type, BaseID, Grade, a `-1` separator, and matching ordered prefix-ID and prefix-value arrays. Signed 16-bit, signed 32-bit and unsigned 8-bit values are decoded distinctly; unsigned 8-bit prefix values such as 208 must not become negative.

**Across the full save (not a single player's inventory): 8,024 manual-like candidate records and 111 distinct BaseIDs.** By Martial Type: Type 1 = 806, Type 2 = 813, Type 3 = 2,016, Type 4 = 4,147, Type 5 = 242. Prefix counts span 3–11. Record regions do not overlap and all accepted prefix ID/value list lengths match.

- 1,861 records use the family-level Skill naming rule `skill_name_middle<BaseID>`. This derivation is not individually constructor-audited for each BaseID.
- 398 records use the three specifically native-verified BaseID/key mappings: `510011→stepName1`, `81001→ability_name_last1`, `88001→ability_name_last8`.
- 2,259 records can be associated with a candidate non-placeholder English base-name component from the existing native localization index.
- 5,765 records do not yet have an adequately evidenced BaseID-to-namekey mapping (particularly other Step and Ability BaseIDs). The decoder does not guess these mappings.

**IMPORTANT:** The `DataUnit.cache` contains many unit records. These 8,024 candidates are **not** confirmed player-owned and **not** the 183 instances previously documented in the private v0.7.x research.
