# Tale of Immortal Android — v0.9.0 Save Unit Boundary Audit

**2026-11-01 | Read-only offline research.** The original game APK, Mod Menu v0.3.6 DEX, native SO, save and previously working features remain unchanged.

## Findings

A hash-pinned reader of the original decompressed `DataUnit.cache` recovered an ordered table of **2,073 distinct six-character unit identifiers**. The table consists of fixed-width, length-prefixed UTF-16 strings, with a declared count that matches its actual length. In the associated unit data, each identifier has **exactly one structurally recognizable unit-ID anchor**, and all **2,073 / 2,073 anchors** occur in the exact same order as the keys. Unlike generic occurrences of unit IDs in NPC relations, these anchors match the required serialized field-marker/string pattern.

Grouping the previously recovered v0.8.9 whole-save manual-like candidates between consecutive structural unit anchors gives:

- **8,024 / 8,024** candidates assigned to unit intervals, with no candidate starting before the first anchor or spanning the next.
- **2,011** units have one or more manual-like candidates; **62** units have none.
- The largest group has **24** candidate manual records.
- **No single unit interval** contains exactly **183** candidates in this particular save snapshot.
- Earlier native-verified Type/BaseID, original Grade, ordered prefixes, name keys, and byte offsets are preserved; no full generated titles or actual UI Levels have been invented.

**Scope limitation:** Structural unit grouping is **not yet proof of player ownership**. The exact `DataWorld.playerUnitID` → `UnitInfoData.unitID` relationship must be checked on the serialized runtime values. The earlier private 183-instance/71-key sample has not been identified within this dataset: it may be a selection across multiple units or a differently scoped research extraction. Do not replace that sample with 183 arbitrary candidates, and do not imply the player has 8,024 manuals.
