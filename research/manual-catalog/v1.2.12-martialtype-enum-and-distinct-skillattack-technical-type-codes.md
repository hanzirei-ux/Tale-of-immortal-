# Tale of Immortal Android — v1.2.12 MartialType enum and distinct SkillAttack technical type codes

**2026-11-03 | Read-only, source-verified analysis.** Original game binaries, AssetBundles, save, APK, `classes2.dex`, and functioning Mod Menu v0.3.6 were not modified.

## Exact native MartialType category values

From the same SHA-256-pinned `global-metadata.dat` v31, the native type definition **`MartialType` (type-definition index 6372)** declares six values (including None). The `fieldDefaultValues` entries reference the `fieldAndParameterDefaultValueData` area of the genuine metadata. Decoding the original **IL2CPP compressed signed integer** defaults yields:

| Native enum numeric value | Native field | User-facing category used in planning |
|---:|---|---|
| **0** | `None` | none |
| **1** | `SkillLeft` | Martial |
| **2** | `SkillRight` | Special |
| **3** | `Step` | Motion |
| **4** | `Ability` | Mind Skill |
| **5** | `Ultimate` | Ultimate |

The stored bytes `00 02 04 06 08 0a` are **compressed signed integer encodings**, not literal enum values 0,2,4,6,8,10. As an independent decoder cross-check, the nearby native `EquipType.Ring` default is encoded `82 5a` and correctly decodes to **301**, consistent with the previously recovered Ring subtype. Thus the enum confirms **Ultimate=5**, but does not classify every individual Skill/Manual BaseID.

## Important separate `ConfBattleSkillAttackItem.type` field

The original `ConfBattleSkillAttackItem` constructor (RVA `0x5d4eccc`) stores the original **`w5` argument** into its own 32-bit `type` object field at offset **`+0x30`**. This is verified by exact ARM64 instructions at `0x5d4ed2c`, `0x5d4ed6c`, and `0x5d4ed7c`. The prior v1.2.4 constructor-argument audit recovered that argument for all **1,568** unique SkillAttack BaseIDs:

| SkillAttack *technical* type value | Native constructor records |
|---:|---:|
| 1 | **1,406** |
| 2 | **31** |
| 3 | **106** |
| 4 | **25** |
| **Total** | **1,568** |

**Do not conflate these numbers with `MartialType`.** The native field `ConfBattleSkillAttackItem.type` is separate from the enum `MartialType`. In particular, raw type 3 is **not** evidence that these 106 SkillAttack records are Motion Manuals. A separate per-BaseID mapping through generated manuals or runtime/manual configuration is required. No exhaustive Martial/Special/Ultimate categorization of SkillAttack BaseIDs is claimed by this milestone.
