# Tale of Immortal Android — v1.2.7 AbilityBase `x3` array provenance (40 empty, 41 three-element)

**2026-11-03 | Read-only, pinned original IL2CPP audit.** No APK, DEX, SO, AssetBundle, save, working Mod Menu, or game-state modification.

## New verified result

Re-disassembled the entire native `ConfBattleAbilityBaseItem` initialization region (`0x5A7D1C0–0x5A80300`) and located **81** direct constructor calls to `0x5A7C82C`, each preceded by its own **array allocation** via wrapper `0x2615A20`. That wrapper branches to `0x25ED620`, whose array allocator implementation calls `il2cpp_array_element_size@plt` and writes native array length at object offset `+0x18`.

The caller supplies the array object as `x3` to the Ability constructor. The constructor saves it at **instance offset `+0x20`** (`str x28, [x0, #0x20]!` after `mov x28,x3`). It is **not** a static UTF-8/localization icon-key string.

| Exact native x2 localization name-key category | Calls | Native allocated array length |
|---|---:|---:|
| `ability_name_first...` | **17** | **0** |
| `ability_name_last...` | **41** | **3** |
| `ability_name_...` (generic) | **19** | **0** |
| Literal `0` name placeholder | **4** | **0** |
| **Total** | **81** | **40** length 0; **41** length 3 |

All **41 length-3** allocation cases have one further native helper call to `0x760ADA8` between allocation and constructor. The helper receives the allocated array and an initialization reference, but the **meaning and element type of those three slots remain unverified**. The array length 0 cases have no such call.

The 81 constructor callsites all pass `x3=x20`; the array allocation return `x0` is preserved in `x20` using `mov x20,x0` at 80 callsites and equivalent `add x20,x0,#0` at one optimized callsite (`0x5A7EC60`). Each is paired to a unique preceding allocation call. Strict source checks preserved and verified the original hash:
